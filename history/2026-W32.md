### [code] `main_branch` auto-detection in the Stop hook
- **What:** Closed the "Harden the hook dispatcher" roadmap item. Added
  `detect_main_branch()` + `resolve_main_branch()` to `hooks/workflow_hook.py` and
  wired the latter into `handle_stop()`, replacing the flat
  `stop_hook.main_branch` lookup that defaulted to `"main"`. Resolution order:
  explicit non-empty `stop_hook.main_branch` → `git symbolic-ref --short
  refs/remotes/<remote>/HEAD` (local ref, no network) → optional `git remote show
  <remote>` `HEAD branch:` parse → `"main"`. Three new config keys
  (`main_branch_autodetect` default true, `main_branch_remote` default `origin`,
  `main_branch_probe_remote` default false) in `schemas/config_schema.json`,
  `.claude/workflow_config.json`, and `templates/workflow_config.json`; the two
  configs now omit `main_branch` so autodetect is the dogfooded path. Resolution
  runs *after* the `stop_hook_active`/block-cap short-circuit and memoises into a
  new `main_branch_detected` state key (persisted even on a non-blocking Stop), so
  a session shells out to git at most once. 11 new tests in
  `TestMainBranchDetection` (precedence, blank-value fall-through, custom remote,
  `(unknown)` HEAD, no-network-by-default, memoisation, and two end-to-end Stop
  cases) — suite 27 → 38, all green.
- **Why:** The hardcoded `main` default mis-fires on every repo whose default
  branch is `master`/`trunk`/`develop`: a dirty tree on the real default branch
  looked like a missed Phase-3 closure and produced a spurious commit reminder on
  every close. The roadmap named `git remote show origin`, but that contacts the
  remote — unacceptable as the primary probe inside `Stop`, which runs while the
  user waits for the session to close. The local `refs/remotes/*/HEAD` ref carries
  the same answer for free (written by `git clone`), so it became step 2 and the
  network probe became opt-in. Explicit pins keep winning, so every existing
  adopter config is unaffected.
- **Refs:** `hooks/workflow_hook.py` · `tests/test_hook.py` ·

### [code] `PreToolUse` Tier-0 guard — three prohibitions become enforceable
- **What:** A fourth handler on the dispatcher (`handle_pre_tool_use`, matcher
  `Bash|PowerShell`) splits each command on the separators the permission matcher
  recognises and runs four guards over every subcommand. `guard_force_push` **denies**
  a force-push whose destination refspec resolves to a protected branch;
  `guard_protected_paths` **denies** `rm` / `Remove-Item` / `git rm` aimed at
  `tier0_guard.protected_paths`; `guard_history_rewrite` **asks** before `--amend`,
  `rebase`, `reset --hard`, `filter-branch`; `guard_heredoc` **asks** on heredocs,
  `-F -` / `--file=-` / `-F /dev/stdin`, and a bare `git commit`. New `tier0_guard`
  config block; 34 tests in `TestTier0Guard`.
- **Why:** `permissions.deny` is the stronger mechanism and does not fit these four.
  Patterns anchor on a literal prefix, so `Bash(git push --force*)` misses
  `git push origin main --force` and `git push -f`; a deny rule carries no exceptions,
  so one broad enough to protect `main` also blocks a topic branch you own; and
  `Bash(...)` / `PowerShell(...)` are separate namespaces, so a Bash-only list is
  bypassed by the other tool. Whether a branch is *shared* is a fact about the
  repository, not the command string — that needs a parser.
- **Risk:** capability — a guard that fires wrongly is worse than none, because it
  teaches the operator to route around it.
- **Refs:** `hooks/workflow_hook.py` · `schemas/hook_contract.md` §PreToolUse ·
  `GUIDE.md` §7.5 · `tests/test_hook.py::TestTier0Guard`

### [decision] `FileChanged` evaluated and rejected; `live` split into deny and ask
- **What:** Two decisions. (1) Claude Code's `FileChanged` event was the obvious mechanism
  for the above — it watches the disk, so it sees writes from any process — and was
  rejected: its matcher is a list of literal filenames and this repo's ledger filename
  rolls over every Monday, so a static watch list would go stale in seven days. (2) Every
  guard-backed artifact now declares `enforcement_mode` (`deny` / `ask`), held to the code
  by `TestEnforcementModeMatchesGuard`.
- **Why:** (1) A watch list that silently stops matching is the "check that could never
  pass" already in `docs/RETROSPECTIVE.md`, and mtime is version-independent and
  indifferent to filenames. (2) `guard_heredoc` escalated a heredoc exactly as designed,
  the prompt was approved, and the rule was broken anyway — and that heredoc is what caused
  the ledger-flag failure above. An `ask` enforces the prompt, not the outcome, so it
  cannot wear the same tier as a `deny` without overstating itself. A prose note would have
  drifted; a field bound to the guard's actual return value cannot.
- **Risk:** accountability — the whole value of the tier vocabulary is that a reader can
  trust what `live` means without reading the implementation.
- **Refs:** `docs/governance-integration-decision.md` §9 · `docs/RETROSPECTIVE.md` ·
