### [code] `main_branch` auto-detection in the Stop hook
- **What:** Closed the "Harden the hook dispatcher" roadmap item. Added
  `detect_main_branch()` + `resolve_main_branch()` to `hooks/workflow_hook.py` and
  wired the latter into `handle_stop()`, replacing the flat
  `stop_hook.main_branch` lookup that defaulted to `"main"`. Resolution order:
  explicit non-empty `stop_hook.main_branch` → `git symbolic-ref --short
  refs/remotes/<remote>/HEAD` (local ref, no network) → optional `git remote show
  <remote>` `HEAD branch:` parse → `"main"`. Three new config keys
  (`main_branch_autodetect` default true, `main_branch_remote` default `origin`,
  `main_branch_probe_remote` default false) in `schemas/config_schema.json`,
  `.claude/workflow_config.json`, and `templates/workflow_config.json`; the two
  configs now omit `main_branch` so autodetect is the dogfooded path. Resolution
  runs *after* the `stop_hook_active`/block-cap short-circuit and memoises into a
  new `main_branch_detected` state key (persisted even on a non-blocking Stop), so
  a session shells out to git at most once. 11 new tests in
  `TestMainBranchDetection` (precedence, blank-value fall-through, custom remote,
  `(unknown)` HEAD, no-network-by-default, memoisation, and two end-to-end Stop
  cases) — suite 27 → 38, all green.
- **Why:** The hardcoded `main` default mis-fires on every repo whose default
  branch is `master`/`trunk`/`develop`: a dirty tree on the real default branch
  looked like a missed Phase-3 closure and produced a spurious commit reminder on
  every close. The roadmap named `git remote show origin`, but that contacts the
  remote — unacceptable as the primary probe inside `Stop`, which runs while the
  user waits for the session to close. The local `refs/remotes/*/HEAD` ref carries
  the same answer for free (written by `git clone`), so it became step 2 and the
  network probe became opt-in. Explicit pins keep winning, so every existing
  adopter config is unaffected.
- **Refs:** `hooks/workflow_hook.py` · `tests/test_hook.py` ·
  `schemas/config_schema.json` · `schemas/hook_contract.md` · `GUIDE.md` §7.2/§7.4
  (v4.7) · `docs/claude-code-hook-integration.md` §3.4/§4/§5.2/§5.3 (v1.12) ·
  `templates/workflow_config.json` · `.claude/workflow_config.json` ·
  `CHANGELOG.md` · `ROADMAP.md` · `python -m unittest discover -s tests` (38 OK)

### [code] Loop detection, `--self-test`, and the governance library
- **What:** Three v14 controls implemented in `hooks/workflow_hook.py`.
  (1) **Loop detection**: `PostToolUse` hashes `(tool_name, tool_input)` into a
  16-char signature, keeps a rolling 20-entry window in session state, and flags a
  run of consecutive identical calls at `loop_detection.repeat_threshold`
  (default 3, clamped to ≥2), logging one JSONL line per loop and announcing each
  signature at most once. (2) **`--self-test`**: validates the config against
  `schemas/config_schema.json` with a stdlib JSON Schema subset, runs health
  checks, and derives a governance maturity level 1–5 written to
  `.ai/00-system/maturity-tracker.json`. (3) **`ANTHROPIC_API_KEY` warning** at
  `SessionStart` and in `--self-test`. Plus the `.ai/` governance library and the
  `templates/ai-library/` adopter scaffold, both tiered `live`/`convention`/
  `declarative`, and `docs/RETROSPECTIVE.md` activating the long-unused
  `retrospective_file` config key. 21 new tests, suite at 63.
- **Why:** These are the four v14 controls that are actually enforceable on Claude
  Code with a Pro subscription and no API key. Everything requiring a second agent,
  key infrastructure, or API access (DIDs, SPIFFE, delegation, shadow-AI detection,
  RAG metrics) is recorded as declarative with the reason attached, so no artifact
  implies enforcement it doesn't have.
- **Risk:** behavioral — loop detection is the first hook output that reacts to
  agent behaviour rather than file paths; kept advisory and announced once per
  signature so it can't become a nag.
- **Refs:** `hooks/workflow_hook.py` · `tests/test_hook.py` (63 OK) ·

### [decision] Tiered adoption instead of verbatim v14 adoption
- **What:** Adopted the full v14 artifact set but assigned every control one of
  three enforcement tiers, and recorded the disposition of all 24 sections in
  `docs/governance-integration-decision.md`. Kept Phase 0–3 canonical and mapped
  the 21-step SOP onto it (GUIDE §12) rather than renumbering. Dropped the RAG
  grounding/attribution/policy-alignment metrics outright rather than stubbing them.
- **Why:** v14 is written for an enterprise agent fleet with API access and key
  infrastructure. Instantiating it verbatim here would have produced artifacts that
  look enforced and are not — which is worse than not having them, because it
  teaches the reader to stop checking. Renumbering to 21 steps would have broken
  every archived plan, ledger entry and hook reference for no behavioural gain.
- **Risk:** design — a governance framework that overstates its own enforcement is
  a design flaw in the workflow itself.
- **Refs:** `docs/governance-integration-decision.md` · `GUIDE.md` §12–§14 ·
  `.ai/README.md`
